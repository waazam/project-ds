# Project DS — Conventions

One architecture for everyone (human or agent) working on this repo.

## Engine
- Godot **4.7.2 .NET** (`C:\Users\Dan\tools\Godot_v4.7.2-stable_mono_win64`), C# / .NET 8, Forward+ on D3D12, Jolt physics.
- The Steam copy of Godot is the non-.NET build and cannot run this project.

## Layout
| Path | Holds |
|---|---|
| `scenes/<area>/` | `.tscn` files, snake_case (`trail_slice.tscn`) |
| `scripts/<area>/` | C# classes, PascalCase file = class name |
| `assets/audio/{ambient,sfx,music,voice}` | `.wav`/`.ogg`: generated by `tools/AudioGen` and `tools/WinterAudio`, plus the owner's own recordings (see `docs/CREDITS.md`); `tools/AudioAudit` scores them |
| `assets/shaders/` | `.gdshader` |
| `assets/{models,textures,fonts,ui,video}` | models (many built in code by `tools/Blender`), baked and scanned textures, fonts, UI art, video |
| `docs/` | the story (`STORY.md`, authoritative), these conventions, credits, the changelog, design and research notes |
| `tools/` | offline console tools; excluded from the game assembly |

## Code
- Namespace mirrors folder: `ProjectDS.Player`, `ProjectDS.Audio`, `ProjectDS.World`, `ProjectDS.Systems`, `ProjectDS.UI`.
- Tabs for indentation. `[Export]` anything a designer should tune.
- Small components over one big script. Nodes find each other through exported `NodePath`s or groups, not deep `GetNode` chains.
- If Godot already does it (SpringArm3D, CharacterBody3D, audio buses), use Godot.

## Audio
- Every sound goes to a named bus. Nature sounds use the category buses (`Birds`, `Insects`, `Wind`, `Distant`, `Water`), which feed `Nature`.
- `ForestAmbienceManager` owns the category bus volumes. **Never set those bus volumes anywhere else.** To make the forest react, place a `SilenceZone`.
- Player sounds go to `Player`, supernatural beds go to `Unnatural`, and dialogue/recordings go to `Voice`.

## Groups
- `silence_zones`: every `SilenceZone`
- `player`: the player body
- `terrain`: the node that answers `HeightAt(x, z)`

## Git
- Commit after each working phase with a short imperative message (`Add player controller`).
- Never commit `.godot/`, `bin/`, `obj/`, or build output.

## Testing
- `-- --autotest` runs the full-story test (`StoryTest*.cs`, Acts 1-25 across both levels, the endings included), walking everything; report and screenshots go to `test-output/story/` (or `test-output/<name>/` with `--test-out=<name>`), exit code 1 on any failed check. `--story-from=N --story-to=M` runs a range of acts (from Act 3 on, the start is seeded from that act's save). With `--measure-walks` it times each long stair and hall walking and running (Acts 11, 14, 15, 17, 21) and fails if running is ever slower; with `--hitches` it logs every frame over 33 ms with its cause (`PerfProbe.cs`, `hitches.txt`).
- `-- --continue-test` runs the Continue round trip for every checkpoint (`ContinueRoundTripTest.cs`); report in `test-output/systems/`.
- `-- --playtest` is the fast functionality test of the whole game (`Playtest*.cs`, driven by `TestBot.cs`): every act, the endings and the core systems (pause menu, settings, key rebinding, run/stamina, crouch, inventory, the audio audit, engine errors, fps) in independent beats. Each beat is seeded from its own save and Continued into (so every act's start is a real Continue), jumps the player next to each trigger and interactable and walks only the last steps into it; long sequences run time-compressed. A failed beat is recorded and the next starts from its own save. `--playtest-only=3,5,13-15` runs those acts (`0` = the systems beat; beat ids like `23c` or `25-3` work too). `--playtest-fast` skips a beat's reload when the beat before it passed and left the story exactly at its save (quicker, but those acts' starts aren't Continued into; the full run and `--continue-test` cover that). Report `test-output/playtest/report.md`, one screenshot per beat, exit code 1 on any failed check. It uses its own per-process save slots and a test settings file, never the player's (and never another test's). Run it after any change that touches gameplay; `--autotest` remains the slow, walk-everything story test.
- **Saves are isolated.** A normal game writes `user://save_*`. `--autotest` and `--continue-test` write the shared `user://test_save_*` slots, so two of them running at once on the same machine (other worktrees included) can trip each other: give each its own `APPDATA`. The playtest writes `user://playtest_save_<pid>_*` and deletes them when it's done. No test touches the player's saves or settings (the tests read and write `user://test_settings.cfg`).
- A new beat goes in the act's `Playtest.<Area>.cs` and the table in `Playtest.Beats.cs` (its seed, its time budget). Drive through `TestBot` (scripted input, `UseIt`/`UseAround`, `ApproachAndWalk`), `Require` what the rest of the beat can't do without, and call `ExpectReload` before anything that leaves the level (a death, a travel, the credits): the beat runs again in the new level with `Phase` one higher.
